# NodeIpoteka

Backend-сервис на NestJS: расчёт ипотечных платежей с историей расчётов, курсы валют с отказоустойчивой
интеграцией, аутентификация на паре JWT-токенов, разграничение прав по ролям, журнал аудита запросов и
справочник доверенных IP-адресов. К проекту приложен небольшой веб-интерфейс на React.

Документация API доступна после запуска на `http://localhost:3000/docs`.

## Что умеет

- **Ипотечный калькулятор** — аннуитетный платёж, общая сумма выплат и переплата; каждый расчёт сохраняется
  за пользователем, который его выполнил.
- **Курсы валют** — данные внешнего источника с кэшированием в Redis, повторными попытками при сбоях и
  резервным источником (парсер cbr.ru) для рубля. Плюс сравнение свежести двух источников и проверка их
  доступности.
- **Аутентификация** — регистрация и вход, пара access/refresh-токенов с ротацией, смена пароля, выход.
- **Роли** — `user` работает только со своими данными, `admin` дополнительно управляет учётными записями,
  видит журнал аудита и справочник доверенных адресов.
- **Аудит** — каждый обработанный запрос попадает в журнал с IP, страной, методом, путём, кодом ответа и
  признаком доверенного адреса.
- **Доверенные локации и адреса** — основа для дополнительного подтверждения подозрительных действий
  (см. раздел «Доверие и подтверждения»).

## Стек

- NestJS + TypeScript
- TypeORM + PostgreSQL
- Redis (кэш курсов, гео-данных и списка доверенных IP)
- JWT (`@nestjs/jwt`), guards, `@nestjs/throttler`, `helmet`
- Axios (`@nestjs/axios`) для внешних интеграций
- Swagger (`@nestjs/swagger`)
- Docker / Docker Compose
- Frontend: React + Vite

## Быстрый старт через Docker

1. Склонировать репозиторий.
2. Создать `.env` в корне по образцу `.env.example` (пустых значений быть не должно — часть переменных
   читается через `getOrThrow`, и приложение не стартует без них). Секреты удобно сгенерировать так:

   ```bash
   openssl rand -hex 32
   ```

3. Поднять стек с чистой базой:

   ```bash
   docker compose down -v
   docker compose up --build
   ```

   Флаг `-v` удаляет тома, иначе Postgres переиспользует данные предыдущего запуска.

4. Приложение — на `http://localhost:3000`, Swagger — на `http://localhost:3000/docs`.

### Что происходит при старте автоматически

`postgres` и `redis` поднимаются первыми и проходят healthcheck (`pg_isready` / `redis-cli ping`); контейнер
`app` дожидается их готовности через `depends_on: condition: service_healthy`. Затем `entrypoint.sh`
последовательно выполняет `npm run db:migrate` (накатывает миграции), `npm run db:seed` (наполняет базу
стартовыми данными) и `npm run start:prod`.

### Если не скачивается базовый образ

Симптом: сборка падает на шаге «load metadata for docker.io/library/node». Причина обычно не в реестре, а в
том, что на хосте сломан IPv6-маршрут: buildkit ходит по IPv6, тогда как сам `dockerd` и `curl` работают по
IPv4. Обходной путь — скачать образ отдельной командой (она идёт через `dockerd`, то есть по IPv4), после
чего сборка возьмёт его из локального кэша:

```bash
docker pull node:24.19.0-alpine
docker compose up -d --build app
```

## Учётные записи

Регистрация через `POST /auth/register` всегда создаёт пользователя с ролью `user`. **Эндпоинта для выдачи
роли `admin` в API нет** — это сделано намеренно, чтобы роль нельзя было повысить снаружи. Поэтому
администратора заводят вручную:

```bash
docker exec -it IpotekaPostgress psql -U <DB_USER> -d <DB_NAME> \
  -c "UPDATE \"user\" SET role = 'admin' WHERE username = 'Alexandr';"
```

Роль попадает в access-токен в момент входа, поэтому после повышения нужно **войти заново** — токен,
выданный до изменения, по-прежнему содержит старую роль.

## Доверие и подтверждения

Раньше белый список IP работал как фильтр «пускать или не пускать» и применялся ко всем запросам. Это плохо
подходило приложению с открытой регистрацией: адреса пользователей динамические, заранее их не перечислить,
а любая ошибка в списке грозила закрыть доступ и самому администратору. Поэтому список перестал ограничивать
доступ и превратился в **источник сигнала о доверии**, который используется в двух местах.

**Первое — журнал аудита.** У каждой записи есть признак `trusted`: пришёл ли запрос с адреса из списка. Это
не защита, а наблюдаемость — по журналу видно, какие действия выполнялись с незнакомых адресов.

**Второе — чувствительные админские операции** (справочник доверенных IP, блокировка, разблокировка, сброс
пароля). Если адрес администратора в списке — операция выполняется как обычно. Если нет — перед выполнением
запрашивается дополнительное подтверждение. Доступ при этом не блокируется: администратор с нового адреса
не окажется заперт снаружи, ему просто нужно будет подтвердить действие.

**Третье — вход в аккаунт.** У каждого пользователя есть свой список подтверждённых городов. Город
регистрации попадает туда сразу. При входе из города, которого в списке нет, запрашивается дополнительное
подтверждение, и только после него город становится доверенным — то есть повторные входы оттуда проходят
без вопросов.

Само подтверждение (предполагается код на электронную почту) **пока реализовано заглушкой**: точка вызова
стоит в нужных местах, но проверка всегда считается пройденной и запрос не прерывает. Подробнее — в
ограничениях ниже.

## Известные ограничения и заглушки

Важно для тестирования: перечисленное ниже — ожидаемое поведение, а не дефекты.

1. **Дополнительное подтверждение не реализовано.** `VerificationService.requireVerification` — заглушка:
   пишет строку в лог и пропускает запрос дальше. Ни вход из нового города, ни админская операция с
   недоверенного адреса сейчас ничего не требуют от пользователя.
2. **Белый список не ограничивает доступ.** Добавление или удаление адресов не влияет на то, отдаёт ли API
   данные. Влияет только на признак `trusted` в аудите и на вызов заглушки подтверждения.
3. **Пока список пуст, доверенных адресов нет.** Поэтому у всех записей аудита `trusted = false` — это
   корректно: «никого не проверяли» не то же самое, что «все проверены».
4. **Геолокация в Docker не работает.** Перед приложением нет обратного прокси, заголовку `X-Forwarded-For`
   мы намеренно не доверяем, поэтому клиент виден по адресу шлюза Docker. Это приватный адрес, для таких
   внешний сервис не опрашивается и сразу возвращается заглушка `Unknown` с `isFallback = true`. Следствие:
   `/geo/me` локально всегда отдаёт заглушку, страна в аудите не определяется, а проверка города при входе
   не срабатывает никогда (нет данных — нет решения).
5. **Отказы уровня guard не аудируются.** Ответы `401` и `403` формируются до контроллера, в журнал не
   попадают.
6. **Сравнение IP точное.** Диапазоны и маски (CIDR) не поддерживаются.
7. **Журнал аудита пока виден любому авторизованному пользователю** — разграничение по владельцу записей
   ещё не сделано (в работе).
8. **Роль `admin` через API не выдаётся** — только правкой в базе, см. раздел «Учётные записи».
9. **Сид добавляет один расчёт без владельца** и выполняется при каждом старте контейнера, поэтому строки
   накапливаются. Такой расчёт не принадлежит никому и обычному пользователю не виден.
10. **Отзыва access-токенов нет.** Выход и блокировка обнуляют refresh-токен, но уже выданный access-токен
    остаётся действительным до истечения срока.

## Разработка без Docker

```bash
npm install
docker compose up -d postgres redis   # нужны только база и кэш
npm run db:migrate
npm run db:seed
npm run start:dev
```

## Миграции

Накатить существующие:

```bash
npm run db:migrate
```

Сгенерировать новую по изменениям в сущностях:

```bash
npx typeorm-ts-node-commonjs migration:generate -d src/data-source.ts src/migrations/ИмяМиграции
```

Через `npm run db:migration:generate` генерировать не нужно: в скрипте зашито конкретное имя миграции, и своё
имя туда не передать — CLI примет только один позиционный аргумент и завершится ошибкой.

Новую сущность нужно зарегистрировать **в двух местах**: в `src/data-source.ts` (его читает CLI при генерации
и накатывании) и в `src/app.module.ts` (его читает само приложение). Если пропустить первое — миграция
получится пустой; если второе — приложение упадёт при старте на поиске метаданных сущности.

## Тесты

### Unit

```bash
npm run test
```

Внешние зависимости замоканы, Postgres и Redis не требуются. Покрыто: guards (`AuthGuard`, `WhiteListGuard`,
`StepUpGuard`), `AuthService` (порядок проверок при входе и запись локации при регистрации),
`VerificationService` (поведение при отсутствии гео-данных, известный и новый город, порядок «сначала
подтверждение, потом запись»), `WhitelistService`, `CurrencyService`, `ResilientHttpService`, `UsersService`,
`MortgageService`.

### e2e

```bash
docker compose up -d postgres redis
npm run test:e2e
```

- `test/auth-currency.e2e-spec.ts` — вход, доступ к курсам с токеном и без, единый формат `503`.
- `test/whitelist.e2e-spec.ts` — CRUD справочника под ролью `admin`, отказ `403` обычному пользователю и
  проверка того, что список больше не ограничивает доступ по IP.
- `test/app.e2e-spec.ts` — корневой `GET /`, поднимает весь `AppModule`.

Спеки запускаются в один поток (`maxWorkers: 1`): они работают с одной и той же базой и параллельно мешали бы
друг другу.

## Frontend

В каталоге `frontend/` — интерфейс на React + Vite: вход и регистрация, калькулятор, история расчётов,
курсы валют, профиль, а также админские панели пользователей, аудита и доверенных адресов.

```bash
cd frontend
npm install
npm run dev
```

Дев-сервер проксирует `/api` на backend, поэтому настраивать CORS не нужно.
